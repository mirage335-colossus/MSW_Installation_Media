# Account-choice installer research and validation

Prepared and tested 2026-09-18 against the downloaded Windows 11 ISO. Validation scope is recorded below.

## Layout and integration

- The prepared boot image places `MediaSetup.cmd` and `winpeshl.ini` in `Windows\System32` of **boot.wim index 2**. The source image had no `winpeshl.ini`; the original source ISO is preserved in the workspace.
- Copy `MSW11-MEDIA.ID` and the `profiles` directory into the installation USB root.
- Do not place an `autounattend.xml` at the USB root. The launcher passes the selected file explicitly.
- The launcher finds the USB by its exact marker contents, rejects multiple matching drives, and calls the media's `sources\setup.exe`.
- Both profiles leave disk selection, partition operations, Windows edition/licensing, locale, privacy choices, and credentials interactive. Neither contains a username, password, auto-logon, disk configuration, or install target.
- Local uses the documented OOBE screen settings plus Rufus's current BypassNRO registry value. Microsoft uses the ordinary online account/network screens and does not set BypassNRO.
- Both disable **Setup Dynamic Update** through the windowsPE answer-file setting. This does not disable Windows Update after installation, and is not proof that OOBE cannot update independently. Keep local-mode installation disconnected until reaching the desktop.
- The initial VM test found that this ISO's `sources\setup.exe` rejects `/DiagnosticPrompt Enable` and exits with code 31, despite Microsoft's general CLI reference listing WinPE support beginning with Windows 11 24H2. The launcher therefore omits that argument and uses only `/unattend:`. The menu still offers a command prompt for troubleshooting. The corrected launcher reached installation and OOBE in both validation VMs.
- The profiles retain an empty `UserData/ProductKey/Key` because Rufus's implementation reports that WinPE answer files otherwise trigger a product-key validation error. `WillShowUI=OnError` retains interactive recovery. Unlike Rufus's generated file, these profiles do not auto-accept the EULA.

## Observed validation and limits

The answer files are well formed and contain no automated disk target or account credentials. Two isolated QEMU VMs booted the prepared media, selected their respective menu paths, retained interactive locale, edition, EULA and disk-selection screens, and installed to disposable 80 GB virtual disks. Both booted Windows independently after the installer USB was detached.

- **Windows 11 Home, local path, disconnected:** reached the interactive “Who's going to use this device?” local-user creation screen, created a disposable VM-only local account, and reached the Windows desktop while still disconnected. Guest diagnostics confirmed `Get-LocalUser` reports `PrincipalSource=Local` and `Confirm-SecureBootUEFI` returns `True`.
- **Windows 11 Pro, Microsoft path, connected through emulated Ethernet:** installed successfully, passed region/keyboard and personal-use selection, and reached “Let's add your Microsoft account” with the email/phone/Skype entry field, Create one, and Sign-in options. No credentials were entered, so account authentication and a cloud-account desktop were not tested. OOBE performed an initial online update/restart; its later optional Windows update stage was deferred with Update later.

These tests cover Home/local and Pro/Microsoft, not all four edition/account combinations. VM success tests the setup/account flow, not physical Lenovo drivers, Wi-Fi, Ethernet, or firmware. Cancellation/restart and missing-media recovery have not been fully exercised. A newer ISO or later OOBE update requires a fresh account-flow test. The final T15g driver additions are separate from the unchanged account launcher/profiles tested here.

## Current evidence

1. **Rufus 4.15, 2026-06-30** is the latest release shown by the primary project release page on 2026-09-18. Its source still implements the online-account requirement checkbox by setting `BypassNRO=1` in the specialize pass. Automatic named-user creation is a separate option. Sources: [release](https://github.com/pbatard/rufus/releases/tag/v4.15), [versioned source](https://raw.githubusercontent.com/pbatard/rufus/v4.15/src/wue.c).
2. **Rufus FAQ, page last edited 2026-07-17** says the account bypass exposes local account creation only when the installer cannot reach the internet. The age makes this useful corroboration, not a guarantee for every new ISO: [FAQ](https://github.com/pbatard/rufus/wiki/FAQ#help-i-dont-see-the-option-to-bypass-the-need-for-a-microsoft-account-with-windows-11).
3. **Schneegans generator, accessed 2026-09-18**, reported commit `4037a44` updated 1–2 days earlier and support through 26H2. Its interactive-local account code removes `UserAccounts` and `AutoLogon`, then sets `HideOnlineAccountScreens=true`. The base template also hides wireless setup. This is active developer-source corroboration for the local profile: [generator](https://schneegans.de/windows/unattend-generator/), [Users.cs](https://raw.githubusercontent.com/cschneegans/unattend-generator/master/modifier/Users.cs), [base template](https://raw.githubusercontent.com/cschneegans/unattend-generator/master/resource/autounattend.xml).
4. **Microsoft HideOnlineAccountScreens documentation, 2020-11-05** specifies the oobeSystem setting and its default false value. It is old documentation and must be verified on the actual image: [setting](https://learn.microsoft.com/en-us/windows-hardware/customize/desktop/unattend/microsoft-windows-shell-setup-oobe-hideonlineaccountscreens).
5. **Microsoft Windows Setup CLI reference, accessed 2026-09-18**, lists `/Unattend` as applicable from WinPE, but `/DynamicUpdate` as **not** applicable from WinPE. Use the XML setting instead: [CLI reference](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/windows-setup-command-line-options?view=windows-11), [DynamicUpdate XML](https://learn.microsoft.com/en-us/windows-hardware/customize/desktop/unattend/microsoft-windows-setup-dynamicupdate), [Enable XML](https://learn.microsoft.com/en-us/windows-hardware/customize/desktop/unattend/microsoft-windows-setup-dynamicupdate-enable).
6. **Microsoft Winpeshl.ini reference, 2021-01-18** supports a replacement shell and `[LaunchApps]` arguments, executing entries sequentially. Hence `wpeinit.exe` followed by `cmd.exe /c` for the menu: [reference](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/winpeshlini-reference-launching-an-app-when-winpe-starts?view=windows-11).
7. **Microsoft Insider announcements, 2025-03-28 and 2025-10-06** document removal of bypassnro.cmd and local-only commands in preview builds. These are reasons to avoid making OOBE console tricks the sole local-account path; they do not establish the behavior of every retail build: [26200.5516](https://blogs.windows.com/windows-insider/2025/03/28/announcing-windows-11-insider-preview-build-26200-5516-dev-channel/), [26220.6772](https://blogs.windows.com/windows-insider/2025/10/06/announcing-windows-11-insider-preview-build-26220-6772-dev-channel/).
8. **PC Gamer hands-on report, 2026-09-14**, says its own non-Insider fresh installation reproduced a local-account bypass via a Learn more link after a September 12 community discovery. It does not specify the exact stable ISO/build. The reported UI behavior is too unstable to use as this media's design: [hands-on report](https://www.pcgamer.com/software/operating-systems/we-tested-the-simple-windows-11-account-bypass-and-it-works-just-no-one-tell-microsoft/).
9. **Microsoft Support, accessed 2026-09-18**, documents switching either account type later through Settings > Accounts > Your info. This remains a convenience after either installation choice: [account conversion](https://support.microsoft.com/en-US/accounts-billing/manage/change-from-a-local-account-to-a-microsoft-account-in-windows).

## E485 compatibility scope

Lenovo's E485 specification lists Ryzen 3 2200U, Ryzen 5 2500U, or Ryzen 7 2700U, with discrete TPM 2.0. These CPUs are absent from the Windows 11 supported AMD list. This is an unsupported-hardware installation regardless of whether the booted installer permits it. Sources: [Lenovo E485 PSREF](https://psref.lenovo.com/syspool/Sys/PDF/ThinkPad/ThinkPad_E485/ThinkPad_E485_Spec.PDF), [Microsoft processor list](https://learn.microsoft.com/en-us/windows-hardware/design/minimum/supported/windows-11-supported-amd-processors).

The default launcher does not turn off TPM, Secure Boot, or RAM checks for all models. Current Rufus source's booted-install bypass changes only `BypassTPMCheck`, `BypassSecureBootCheck`, and `BypassRAMCheck`; it does not implement the often-repeated `BypassCPUCheck` registry value. No fresh primary evidence was found that a separate CPU allowlist bypass is necessary for the E485 on the exact retail ISO. Verify its clean-install behavior. Do not confuse official CPU support with the CPU instruction requirements that newer Windows kernels actually need.
